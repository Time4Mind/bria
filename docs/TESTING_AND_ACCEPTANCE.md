# Проверки и приёмка

Статус документа: обязательный контракт реализации. Для текущего этапа 2 доступны контекстные и архитектурные проверки, модульные и интеграционные тесты, race detector, vet, сборка coordinator и двух provider adapters, локальный config preflight и identity-only Telegram preflight. Готовность к выпуску и внешняя live-приёмка не заявляются. Критерии ниже нельзя ослаблять без явного решения Артёма.

## Принятое решение

Во время разработки запускаются быстрые проверки только изменённых компонентов и их непосредственных связей. Полный набор проверок выполняется перед каждым выпуском версии, а не после каждого небольшого изменения.

Успешная команда, число пройденных тестов, статус процесса или созданный файл сами по себе не доказывают готовность. Для каждого критичного сценария нужен физический результат - наблюдаемое состояние системы или подтверждение от внешней системы, которое доказывает именно ожидаемое действие.

Числовые требования к задержкам не устанавливаются. Интерфейс принимается, если в пользовательских сценариях нет заметных зависаний и новая версия не стала хуже принятой базовой версии при сопоставимых условиях.

## Термины

- **Быстрая профильная проверка** - короткая проверка изменённого поведения и ближайших связей с другими компонентами.
- **Полный набор проверок** - все обязательные проверки выпуска на всех поддерживаемых способах запуска.
- **Условие выпуска** (`release gate`) - обязательный критерий, без которого версия не выпускается.
- **Пробный сквозной запуск** (`smoke test`) - короткий запуск настоящей системы от пользовательского действия до наблюдаемого результата.
- **Подтверждение результата** (`receipt`) - прочитанное после действия состояние или ответ внешней системы, позволяющий отличить успех, отказ и неопределённый результат.
- **Базовая версия** (`baseline`) - последняя принятая версия, с которой сравнивается новая версия в одинаковом окружении и на одинаковом сценарии.

## Текущая проверяемая граница этапа 2

Локальный полный набор запускается командой:

```sh
make check-full
```

Он проверяет policy и ссылки репозитория, форматирование и архитектурные границы, выполняет `go test ./...`, `go vet ./...`, race tests и собирает исполняемые файлы `bin/bria`, `bin/bria-codex-adapter`, `bin/bria-claude-adapter`.

Перед рабочим запуском применяются три разные команды с разными последствиями:

```sh
bin/bria check-config --config /absolute/path/to/config.json
bin/bria check-telegram --config /absolute/path/to/config.json
bin/bria run --config /absolute/path/to/config.json
```

- `check-config` читает и проверяет локальную конфигурацию, Telegram token, callback key, provider commands, соседние adapter binaries и очищенное окружение исполнителей. Он не обращается к Telegram и не захватывает рабочую instance lock.
- `check-telegram` вызывает только `getMe` и подтверждает точное имя ожидаемого бота. Он не вызывает `getUpdates`, не устанавливает backlog fence и не запускает исполнителей.
- `run` захватывает exclusive lock для state path, перечитывает секреты, компонует runtime и запускает Telegram loop. При отсутствии checkpoint первый запуск после проверки identity устанавливает и сохраняет backlog fence до обработки новых сообщений.

### Классификация текущих доказательств

- **Production-wired / локальные тесты:** `run` подключает Bot API source/sender, owner/chat gate, durable state и message journal, session lifecycle/recovery/supervision, provider runtime, Telegram controller, signed callback flow, interactions, authorization boundary, receipt reconciliation и safe-log cleanup. Эти границы покрыты модульными и интеграционными тестами текущего репозитория, включая synthetic provider children и fake Telegram transport.
- **Только компонентные тесты:** media/file custody, speech preparation, backup/restore, update/rollback и network multi-computer runtime проверяются своими тестами, но не подключены к полному production runtime path.
- **External-unverified:** настоящий пользовательский inbound Telegram flow, реальные Codex/Claude submit и authorization, внешняя доставка медиа/файлов, multi-computer/executor role, Linux/WSL/Docker и физические backup/update probes. Для них нет внешнего receipt; отсутствие receipt блокирует выпуск.

## Проверки во время разработки

Для каждого изменения владелец области обязан:

1. Проверить изменённое поведение через публичную границу компонента, а не только его внутреннюю функцию.
2. Проверить ближайший связанный компонент, если меняется формат данных, состояние или порядок событий.
3. Для исправления дефекта сначала воспроизвести наблюдаемую ошибку, затем доказать тем же сценарием исправленное поведение.
4. Сохранить минимальное подтверждение результата: вход, ожидаемый результат, фактический результат и сведения об окружении.

На этом этапе полный набор по всем платформам не требуется, если изменение не затрагивает общий формат данных, безопасность, обновление, восстановление или платформенную границу. Такие изменения проверяются на всех непосредственно затронутых средах до объединения.

## Обязательные условия выпуска

### 1. Пользовательское поведение

Должны пройти сквозные сценарии Telegram-интерфейса и жизненного цикла сессий:

- создание новой сессии и продолжение существующей сессии Codex и Claude;
- переключение активной и фоновых сессий без остановки их работы;
- карточки, перелистывание истории, отдельный финальный ответ активной сессии и уведомление о завершении фоновой;
- управление `Остановить`, `Закрыть`, `Опции` и общей настройкой `Screen`;
- текстовый и голосовой ввод с переходами `🙋‍♂️`, `👨‍💻` и `🙅‍♂️`;
- приём фотографий и допустимых текстовых подписей без скачивания видео;
- автоматическое обнаружение файлов в финальном ответе, единое уведомление об ошибке для группы файлов и ручной повтор только недоставленных файлов;
- единый архив сессий Codex и Claude без разделения по приложению, из которого они были запущены;
- срок жизни сессии: `никогда`, 6, 12, 24 или 48 часов от создания либо восстановления; занятая сессия закрывается только после завершения текущей работы;
- настройки из Telegram и локального файла показывают одно состояние, а ошибочное изменение целиком отклоняется.

Подтверждение: сохранённая запись фактических сообщений и кнопок Telegram, перечитанное состояние сессии и, где применимо, идентификатор принятого Telegram-сообщения. Снимок экрана без проверки внутреннего состояния недостаточен.

### 2. Параллельная работа и порядок сообщений

Должно быть доказано, что:

- сообщения одной сессии передаются агенту по порядку получения;
- уточнение попадает в уже выполняющуюся работу, не ожидая финального ответа, когда Codex или Claude способен принять ввод;
- очередь переживает перезапуск и не теряет ранее принятые сообщения;
- при заполнении настраиваемого предела новые сообщения отклоняются, а принятые не удаляются и не заменяются;
- разные сессии и разные компьютеры работают параллельно без взаимной блокировки;
- позднее событие фоновой сессии не перетирает открытую пользователем старую страницу другой карточки;
- повтор после неопределённого ответа не создаёт незаметных дублей.

Подтверждение: журнал последовательности с устойчивыми идентификаторами сообщений, состояние очереди до и после перезапуска и фактическая история соответствующего агента. Одного порядка записей во внутреннем тестовом хранилище недостаточно.

### 3. Восстановление после сбоев

Проверки должны по отдельности останавливать процесс агента, исполнитель, координатор и сетевую связь. Они обязаны доказать, что:

- идентификатор сессии, исполнитель, рабочая папка и принятые сообщения не теряются;
- после возврата того же компьютера продолжается та же сессия, а новый независимый контекст не создаётся;
- недоставленные результаты сохраняются и отправляются после восстановления связи;
- при невозможности восстановить архивную сессию архив не меняется, а пользователь получает понятную ошибку и подсказку обратиться к агенту из новой сессии;
- другой компьютер не назначает себя координатором автоматически;
- ручная передача роли координатора возможна только при работающем прежнем координаторе и завершается проверкой нового состояния.

Подтверждение: идентификатор сессии и её история до сбоя и после восстановления, перечитанная очередь, фактический процесс исполнителя и состояние координатора. Статус `запущено` без продолжения исходной сессии не является успехом.

### 4. Архитектурные границы

Автоматическая проверка структуры должна запрещать:

- зависимость ядра сессий и очередей от Telegram;
- смешивание интеграций Codex и Claude с общей логикой жизненного цикла;
- запись общих настроек в несколько независимых хранилищ;
- автоматический выбор или голосование за координатора;
- обход единого слоя надёжного хранения сообщений;
- удаление или ослабление обязательных правил параллельной разработки из `AGENTS.md`.

Новый исполнитель должен подключаться через явно описанную границу, не требуя изменений в Telegram-интерфейсе, очередях и жизненном цикле сессий. Конкретное направление зависимостей фиксируется в архитектурном документе до появления соответствующих пакетов.

Подтверждение: проверка фактического графа зависимостей исходного кода и отдельные проверки запрещённых связей между пакетами. Текстовая схема без сопоставления с кодом недостаточна.

### 5. Безопасность

Полный набор обязан подтвердить:

- Telegram принимает управление только от одного заданного владельца;
- секреты авторизации Codex и Claude остаются только на выбранном компьютере;
- сообщения с кодами и секретами удаляются из Telegram после обработки и не попадают в журналы, резервную копию, диагностические файлы и артефакты выпуска;
- отключение исполнителя не удаляет сохранённую локальную авторизацию, а повторное включение не требует нового входа, пока сама авторизация действительна;
- подписанные файлы обновления проверяются до запуска;
- контейнер не получает неоговорённый доступ к рабочим папкам и данным основной системы;
- повреждённые настройки и резервная копия отклоняются без повреждения действующего состояния;
- подробные журналы автоматически удаляются через 6 часов, служебные - через 24 часа, критические события - через 72 часа.

Проверки используют только тестовые секреты. Дополнительно сканируются исходный код, журналы, резервная копия и собранные артефакты. Успех сканера не заменяет проверку фактического места хранения и удаления сообщения из Telegram.

### 6. Обновление и возврат версии

Выпуск должен пройти последовательное обновление сети компьютеров:

1. Исполнители обновляются по одному.
2. После каждого обновления проверяются запуск, связь, доступность прежних сессий и выполнение пробной задачи.
3. Координатор обновляется последним.
4. Если новая версия не запускается или не проходит проверку, компьютер возвращается к предыдущей рабочей версии.
5. После возврата перечитываются версия, состояние очередей и доступность прежних сессий.

Отдельно проверяются: повреждённый файл обновления, неподходящая платформа, сбой во время установки, отказ запуска новой версии и недоступность одного исполнителя. Обновление остальных компьютеров не продолжается после первого неподтверждённого результата.

Подтверждение: фактически запущенная версия на каждом компьютере, успешная пробная задача после обновления и после принудительного возврата, а также отсутствие потерянных или повторно переданных сообщений.

### 7. Резервная копия

Проверка создаёт одну последнюю резервную копию, повреждает рабочее состояние в изолированной среде и восстанавливает:

- настройки системы;
- список подключённых компьютеров;
- список и состояния сессий;
- недоставленные сообщения;
- полную текстовую историю Codex и Claude;
- Harness - локальные правила, настройки, проверки и состояние вспомогательного контура разработки.

Копия не должна содержать фотографии, созданные и исходящие файлы, архивные пакеты сессий, проекты, журналы, исполняемые файлы, Parakeet, кэши, токены, ключи подключения и данные авторизации. Новая копия заменяет прежнюю только после проверки целостности; одновременно хранится ровно одна проверенная версия.

Подтверждение: сравнение разрешённого состояния до потери и после восстановления плюс отрицательная проверка запрещённых данных внутри фактической копии.

## Матрица поддерживаемых сред

Перед выпуском должны быть проверены macOS, обычный Linux, WSL - Linux-среда внутри Windows - и Docker. В Docker полноценно проверяются обе роли: координатор и исполнитель, включая запуск Codex и Claude с явно подключённой рабочей папкой.

| Среда | Сборка и запуск | Сессии и очередь | Обновление и возврат | Реальные Telegram, Codex и Claude |
| --- | --- | --- | --- | --- |
| macOS | обязательно | обязательно | обязательно | обязательно |
| Linux | обязательно | обязательно | обязательно | обязательно |
| WSL | обязательно | обязательно | обязательно | обязательно |
| Docker: координатор | обязательно | обязательно | обязательно | обязательно |
| Docker: исполнитель | обязательно | обязательно | обязательно | обязательно |

Реальный сквозной запуск нельзя заменять имитацией протокола. Он проводится с тестовой рабочей папкой и отдельными тестовыми сессиями, но через настоящие Telegram, Codex и Claude. Если внешний сервис недоступен, результат помечается `не проверено`, выпуск блокируется, а отсутствие доступа не выдаётся за дефект авторизации без явного ответа сервиса об отказе.

## Проверка отсутствия заметных зависаний

Для каждого поддерживаемого окружения один и тот же пользовательский маршрут выполняется на базовой и новой версиях:

1. Открыть список сессий и активную карточку.
2. Отправить текст в свободную и занятую сессию.
3. Переключиться между активной и фоновой сессиями во время поступления событий.
4. Перелистать историю и дождаться финального ответа.
5. Открыть настройки и переключить `Screen`.

Фиксируются версии, компьютер, способ запуска, состояние сети, сценарий и наблюдаемые задержки. Выпуск блокируется, если интерфейс перестаёт отвечать пользователю, действие требует повторного нажатия без показанной ошибки, карточка перестаёт обновляться без объяснения либо новая версия устойчиво ощущается медленнее базовой на повторяемом сценарии. Числовой порог из этих наблюдений автоматически не вводится.

Для первой версии, у которой ещё нет принятой Bria-базы, сравнение с CC-ботом или `bria-legacy` допустимо только для одинакового сценария в одинаковом окружении. Несопоставимые результаты не объединяются. Первая принятая версия сохраняет собственные результаты как базу для следующего выпуска.

## Отчёт о выпуске

Отчёт должен разделять:

- **Проверено** - сценарий, среда, версия, фактический результат и ссылка на подтверждение;
- **Вывод** - почему совокупность подтверждений позволяет принять версию;
- **Не проверено или заблокировано** - точная граница, причина и влияние на выпуск.

Минимальный набор подтверждений включает:

- идентичность собранной и фактически запущенной версии;
- результаты полного набора по матрице сред;
- записи реальных сквозных запусков Telegram с Codex и Claude;
- результаты сценариев параллельности и восстановления;
- доказательство обновления и принудительного возврата;
- состав и пробное восстановление последней резервной копии;
- проверку архитектурных границ и отсутствия секретов.

Любая невыполненная обязательная строка матрицы или неподтверждённое условие выпуска блокирует выпуск. Исключение возможно только по отдельному явному решению Артёма с записанной областью риска.

## Основание, а не перенос реализации

В `ccbot` есть проверки карточек, перелистывания, маршрутизации сообщений, архивирования и восстановления. В `bria-legacy` есть проверки архитектурных зависимостей, последовательности сообщений, восстановления, установки, контейнерного запуска, обновления и возврата версии. Это подтверждает полезность соответствующих зон проверки, но не делает прежний код или прежнюю распределённую архитектуру частью новой Bria.

Конкретные тесты новой Bria должны проверять решения нового проекта. Копирование старого теста допустимо только после сопоставления его предпосылок с текущими продуктовыми решениями.
