# Сохраняемые планы страниц уведомлений

Согласованный вариант A22 revision 3: новая доставка сохраняет точные Rich
Markdown-страницы до первой отправки. Повторный вызов и открытие после перезапуска
используют сохранённые страницы, даже если код рендера уже изменился.

## Границы

Рабочая сборка подключает FilePartReceiptStore через singlemachinecomposition.
Файл остаётся прежним: `<StatePath>.telegram-notification-parts.json`.
Настройка для включения не требуется. Это формат состояния, не новая версия
продукта и не команда установки.

Deliver использует стабильный OperationID. Notify с таким ID и этим хранилищем
делегирует в Deliver. Временный Notify без ID использует тот же Rich-пагинатор,
но не получает гарантии восстановления: без идентификатора нельзя отличить
повтор от нового одинакового уведомления. Совместимые пользовательские реализации
старого PartReceiptStore без API планов сохраняют прежний путь; рабочий файловый
store реализует новый API. Отправка файлов, фотографий и карточная пагинация не
меняют своих договоров.

## Формирование и восстановление

Новые страницы включают префикс уведомления и окончательную нормализацию таблиц.
Лимит 4096 байт проверяется на финальном Markdown, после добавления оформления
и повторения заголовков. Кодовые блоки и UTF-8 сохраняются; непомещающаяся целиком
строка таблицы или обёртка передаётся ограниченными текстовыми частями без потери
содержимого, но без обещания исходного оформления на такой границе.

План связывается с hash исходных chat/session/kind/text. Изменение любого из них
для прежнего OperationID отклоняется до отправки. Операция LoadPlan не запускает
пагинатор и не меняет файл. План и весь файл состояния имеют контрольные суммы:
потеря отдельного плана, перестановка страниц или повреждение состояния не должны
создавать новую привязку. Это контроль случайного повреждения, не защита от
злоумышленника, способного переписать файл и пересчитать суммы.

Права файла 0600; сохранение выполняется через временный файл, fsync, atomic
rename, fsync каталога и повторное чтение. Локальная и межпроцессная блокировки
защищают создание планов и изменение подтверждений. Тексты страниц не добавляются
в журналы или сообщения об ошибках. Существующий лимит файла 8 MiB сохранён:
при переполнении новая операция не отправляется; автоматического удаления старых
подтверждений и планов нет.

## Совместимость начатых доставок

Формат файла v1 читается без автоматической перезаписи при Open. Если для операции
уже есть запись в operations, при создании её плана сохраняется старое разбиение
и прежние part IDs. Даже пустая запись после явного разрешения повторной попытки
остаётся признаком старой операции. Это действует и после обновления файла из-за
другой, новой операции.

Старые страницы могут превышать новый байтовый лимит после Rich-нормализации:
они сохраняются точно, а не пересчитываются ценой потери соответствия receipt.
У v1 не было hash исходного текста; первая фиксация старого плана использует
исходное уведомление из durable-очереди. Несовпадение старых part IDs/числа частей
блокирует миграцию. После фиксации input binding неизменяем.

Первый сохранённый план переводит файл в формат v2, сохраняя старые receipts и
unknown. Старый бинарник не умеет читать v2 и должен отказать безопасно.
Откат только бинарника на версию до поддержки планов поэтому не поддерживается.
Нельзя удалять plans, понижать version или подставлять старую копию receipts:
это может потерять сведения об уже отправленных сообщениях. Нужен совместимый
бинарник; отдельное восстановление состояния требует согласованной сверки доставок.

## Попытка отправки

Перед HTTP-запросом ClaimPart атомарно сохраняет unknown. Только победитель
может отправлять; другой процесс или вызов увидит claim либо подтверждение.
После положительного Telegram receipt записывается confirmed. Сбой после отправки,
но до сохранения receipt оставляет unknown: автоматической повторной отправки нет.

Только достоверный отказ позволяет снять claim. ErrDeliveryUnknown имеет приоритет
над HTTP-кодом: в частности, HTTP 408 не снимает unknown. Сетевой обрыв, неопределённый
ответ и отсутствие положительного receipt также не вызывают retry/fallback.
Явные ResolveUnknownConfirmed/ResolveUnknownForRetry остаются отдельными действиями
сверки; этот механизм не разрешает их автоматическое использование.

## Проверки

Профильные тесты находятся в notificationplan, notificationstate и telegramnotify.
Сквозные проверки используют реальные временные файлы и исходящий HTTP JSON:
сохранение до send, повторное открытие, frozen payload от другого рендера,
целостность строк таблиц и лимита, v1-совместимость, input conflict, два отправителя,
восемь отдельных процессов, crash после claim, потерю подтверждения и HTTP 408.
Повреждённый файл не переписывается и не приводит к HTTP-запросу.

Локальные проверки не доказывают установку версии или видимый рендер Telegram.
Установка, перезапуск и живое сообщение требуют отдельного разрешения.
