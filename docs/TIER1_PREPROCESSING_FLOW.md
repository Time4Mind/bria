# Tier 1: препроцессинг пользовательского запроса

Статус: **согласовано владельцем; lifecycle фоновой сессии реализован локально
2026-09-10**. Внешняя приёмка через обычный Telegram-запрос остаётся отдельной
границей. Технические сессии одноразовые и не хранят историю запросов.

## Пользовательский flow

| Шаг | Согласованное поведение |
|---|---|
| 1. Приём | Функция по умолчанию выключена. После приёма текстового запроса карточка показывает исходный текст как `🙋‍♂`. Для голоса сначала виден этап распознавания, затем исходная расшифровка Parakeet как `🙋‍♂`. |
| 2. Обработка | При включённой функции исходный текст получает заранее готовая скрытая сессия дешёвой модели на той же ноде. Сразу после занятия сессии Bria запускает следующую. Основная модель в это время запрос ещё не получает. |
| 3. Успех | Та же запись карточки заменяется на `🙋‍♂ <очищенный текст>`. После точного подтверждения основной модели она становится `👨‍💻 <очищенный текст>`. Отдельного сообщения об успехе нет. |
| 4. Ошибка | Карточка показывает `❌ Ошибка препроцессинга`, следом исходный запрос. Исходный запрос сразу идёт основной модели; после подтверждения сохраняется строка ошибки и статус запроса меняется на `👨‍💻`. Ошибка препроцессинга никогда не блокирует коммуникацию. |

## Изоляция и выбор модели

| Правило | Реализация версии 1 |
|---|---|
| Контекст | В thread попадают только встроенная либо пользовательская инструкция и один текущий текст. После durable acceptance thread закрывается; история основной сессии и прошлых препроцессингов не передаётся. |
| Возможности | Отдельный `bria-codex-adapter` process group заранее запускает Codex app-server и ephemeral thread в пустой временной директории, с read-only sandbox, без shell/browser/app tools и без запросов подтверждения. Технический thread не показывается в каталоге Bria. |
| Выбор | На локальной ноде первым используется Codex `gpt-5.6-luna`. Если Codex недоступен, сохраняется stateless fallback на Claude Haiku `claude-haiku-4-5-20251001`; для него готовность до первого запроса не подтверждается текущим adapter API. |
| Сброс | Изменение provider-настроек либо ошибка выбранного provider инвалидирует незанятую сессию и сразу запускает новую. Занятый thread сохраняется до durable acceptance своего результата. |

Один пользовательский запрос создаёт не более одного LLM-вызова
препроцессинга. Повтор lease до durable acceptance получает уже рассчитанный
результат. После двух живых timeout при лимите 5 секунд (medium и low)
пилотный предел 2026-09-06 увеличен до 10 секунд, reasoning явно low.
Это не измеренные p50/p95 и не утверждение о гарантированной задержке.
App-server принимает явный запрос `model=gpt-5.6-luna`, но не возвращает
независимый receipt фактически тарифицированной модели. Поэтому поле `model`
в lifecycle означает requested model, а `model_evidence` остаётся пустым.
Успех и cache/fallback журналируются отдельно без исходных текстов.

## Команды, вложения и размер

| Случай | Поведение |
|---|---|
| Slash-команда | Команда без аргументов либо с 1–3 аргументами обходит препроцессинг. При 4 и более аргументах текст обрабатывается обычно. |
| Вложения | Бинарное вложение и его custody не меняются; переписывается только текст или подпись. Вложения не считаются аргументами slash-команды. |
| Результат | Принимается только непустой валидный UTF-8 текст без NUL. Tools/структурированные ответы и превышение пропорционального лимита считаются ошибкой с fallback на исходник. |
| Инструкция | Пустое пользовательское значение означает встроенную инструкцию. Пользовательская инструкция полностью заменяет встроенную; общие ограничения изоляции сохраняются. |

Пилотный предел результата: не более максимума из тройного размера исходника
и размера исходника плюс 1024 байта, с техническим потолком 1 MiB. Формула
может быть скорректирована по фактическим запросам без изменения flow.

## Надёжность и наблюдаемость

| Правило | Поведение |
|---|---|
| Порядок | Pool допускает одну занятую и одну запускаемую/готовую техническую сессию. Дополнительные запросы ждут durable acceptance предыдущего, поэтому контекст и результаты не смешиваются. |
| Crash до обработки | Журнал хранит исходник и зафиксированную на момент приёма инструкцию; незавершённый элемент повторяется после восстановления lease. |
| Crash после обработки | Выбранный очищенный текст либо решение использовать исходник записывается в тот же журнальный элемент до передачи основной модели. Повторный запуск не вызывает препроцессор заново и не создаёт второй submit основной модели. |
| Отключение настройки | Влияет только на сообщения, принятые после изменения. Уже принятый элемент заканчивает зафиксированный flow. |
| Ошибка | Safe-log получает `prompt.preprocessing_failed` и lifecycle `prompt.preprocessing_session`: `starting`, `ready/degraded`, `responded/failed`, `accepted`, `closed/close_failed`. Startup и close имеют bounded cancel/kill/wait. Исходный пользовательский текст в технический лог не пишется. |

Расходы препроцессора входят в обычную квоту выбранного провайдера и поэтому
естественно отражаются в экране `Статус` при следующем обновлении квот.

## Не входит в текущий flow

Контекстная сессия-сателлит для каждой основной сессии не используется. Такая
сессия смешивала бы запросы и меняла согласованную гарантию: один технический
thread обрабатывает ровно один запрос, после чего закрывается.
