## Уточнение A44.1: очередь не является началом ответа

Артём уточнил обязательное правило: прохождение очереди Bria и принятие запроса
Codex не означают, что модель уже начала следующую итерацию. Пока новая итерация
не началась, продолжающие поступать model events относятся к предыдущей
итерации и должны проецироваться выше ожидающего запроса.

Проверка текущего эпизода:

- исходный native turn начался в 09:39:31 MSK;
- второй user message записан в native rollout в 09:46:34.865 MSK внутри того
  же turn;
- следующий assistant commentary записан в 09:46:50.477 MSK;
- отдельного `task_started`, нового turn ID или иного сохранённого события
  начала модельной итерации между ними нет;
- текущий `turn/steer` RPC возвращает тот же turn ID и Bria сразу сохраняет
  accepted, поэтому этот receipt сам по себе не позволяет доказать применение
  запроса моделью.

Согласованный fallback: сначала проверить отдельной live Luna-сессией, даёт ли
Codex устойчивую машинную границу `queued -> applied/model iteration started`.
Если такой границы нет или она требует хрупкой эвристики, не усложнять runtime:
фиксировать запрос в карточке сразу и дальше сохранять append-only порядок без
перестановки уже показанных блоков. Этот вариант считается прозрачнее текущего
поведения даже без точной маркировки момента применения моделью.

Live probe ограничен временными Codex/Luna-сессиями, одним исходным turn и
тремя steer-запросами в каждом прогоне. Он не использует Telegram, live Bria
state/config или рабочую пользовательскую сессию.

Официальный steering-контракт также разделяет `accepted` и применение input:
accepted означает владение поставленным в очередь input, а commit point -
создание successor response. Следовательно, целевой дизайн обязан получить или
вывести отдельную доказуемую границу model-iteration commit; время, accepted и
совпадающий native turn ID для этого недостаточны.

### Результат live-проверки 2026-09-11

Три изолированных реальных прогона Luna, всего девять `steer`, подтвердили
устойчивое разделение RPC receipt и фактического добавления user input:

- в контрольном прогоне три `turn/steer` были приняты за 0 ms, а три точных
  `userMessage.clientId` появились через 0.94-1.03 s; следующий reasoning
  начался только после них, final содержал все три маркера;
- в прогоне во время streaming-commentary три RPC были приняты в
  10:11:32.789 MSK, но старый commentary продолжался до 10:11:38.768 и старая
  command завершилась позже; userMessage появились только в
  10:11:40.552-10:11:40.637, следующий reasoning - в 10:11:42.833;
- повтор дал тот же порядок: RPC в 10:13:20.916, старый commentary до
  10:13:28.525, старая command до 10:13:29.558, userMessage в
  10:13:29.605-10:13:29.687, следующий reasoning в 10:13:31.150;
- в третьем прогоне модель не вывела запрошенные маркеры, хотя userMessage были
  физически записаны. Поэтому эта граница доказывает применение input к turn,
  но не обещает исполнение содержания моделью - это корректное ограничение.

В текущем native CLI режиме rollout не содержит исходный Telegram `clientId`,
но содержит отдельный user-message record в точном физическом порядке. Bria
уже сопоставляет этот record с ещё не принятым input по точному тексту и FIFO;
одинаковые повторные тексты также разрешаются в порядке очереди. Значит новый
provider protocol не нужен: требуется сохранить для каждого model event owner
последнего фактически принятого user record, а не корневой request всего turn.

Целевые состояния для согласования:

| Состояние | Машинная граница | Положение ответа |
|---|---|---|
| `queued_bria` | запрос сохранён, но ещё не передан | продолжающийся ответ остаётся выше запроса |
| `queued_codex` | отправка выполнена, user record ещё не прочитан | продолжающийся ответ всё ещё выше запроса |
| `active_iteration` | прочитан exact/FIFO-matched user record; затем начинается model item | новые model events закрепляются после этого запроса |
| `completed` | terminal текущего native turn | final относится к последнему применённому запросу/пакету |

Fallback с немедленной постоянной фиксацией позиции не требуется: доступная
граница повторилась во всех трёх прогонах. Сам запрос можно показывать сразу как
ожидающий; постоянным владельцем последующих model events он становится только
после matched user record. В активном эпизоде `783531735` user record был в
09:46:34.865 MSK, следующий reasoning - в 09:46:45.911, а commentary-ответ - в
09:46:50.477. Следовательно, этот конкретный ответ действительно должен быть
ниже `783531735`; дефект вызван сохранением root-owner `783531733`.

Уточнение Артёма для Claude Code: целевая семантика порядка та же. Если текущая
среда Claude даёт устойчивый native user boundary, переключать owner по ней.
Если такой доказуемой границы нет, использовать согласованный append-only
fallback: сразу закрепить позицию запроса и больше не переставлять уже показанные
события. Нельзя переносить Codex-специфичную эвристику в Claude без отдельной
проверки реального transcript/runtime формата.

## Блок A44.2: режим страницы - фактическое расхождение

| Ситуация | Сейчас | Целевой флоу |
|---|---|---|
| Любой новый пользовательский запрос | Основной ingress уже создаёт новый carrier, но проецирует в него сохранённый page plan предыдущей карточки | Сохранить создание нового carrier, но всегда открыть его последнюю страницу и поставить `FollowLatest=true` |
| Публикация final | `completionPageView` всегда ставит `FollowLatest=false`, даже если начало final одновременно является последней страницей | Новая карточка открывает начало final; отдельно сохранить факт, находился ли пользователь на хвосте |
| Параллельный prompt-status | Может начать edit старого carrier одновременно с send нового | После границы нового input запретить любые фоновые edit предыдущего carrier |
| Рост и ручная навигация | После корректного `follow=true` рост следует; earlier page фиксирует, Latest возвращает follow | Оставить внутри новой карточки; следующий input снова создаёт новую карточку с follow |

Live evidence активной `workdir7`: в 09:38:22 MSK final создал состояние
`8/8, follow=false`; первый рост нового запроса в 09:39:26 сохранил `8/9,
follow=false`. Только ручной `page_latest` в 09:39:59 перевёл карточку в
`9/9, follow=true`. Текущее persisted состояние после следующего короткого final
снова `24/24, follow=false`, поэтому тот же дефект готов повториться при новом
запросе.

Уточнение Артёма заменяет предварительное ограничение только новым root после
final. Любой новый пользовательский input является границей нового Telegram
carrier, включая steer во время работающей генерации, текст, голосовой и input с
вложением. Старая карточка остаётся физически неизменной на выбранной странице.
Новая содержит актуальную историю и новый prompt, сразу открывается на последней
странице с `FollowLatest=true`. Пока следующего input нет, commentary/tool events
редактируют только этот новый carrier; final снова создаёт отдельную карточку и
открывает начало ответа.

Исправление диагноза: основной ingress уже создаёт новую карточку на каждый
prompt. Ошибочным был вывод по одному `telegrampromptcomposition` без полного
delivery path. Live flow в 10:10:15 MSK подтвердил `card.send_started` новой
карточки `22/22, follow=true`; параллельно отдельный prompt-status начал
`card.edit_started` старого carrier. Проблемный эпизод в 09:39:25 подтвердил
точное отклонение: новая карточка действительно была отправлена, но унаследовала
`8/9, follow=false` вместо обязательных `9/9, follow=true`. Следовательно,
создание carrier сохраняется; исправлять нужно начальный page plan новой карточки
и fence фоновых edits старого carrier.

План страницы хранится между обновлениями и повторным открытием сессии. Поэтому
возврат из меню не должен сам менять фиксированную страницу на хвост или наоборот.
Любая навигация пользователя меняет сохранённый план до следующего явного
перехода; поздний background edit не имеет права восстановить старый план.

## Coverage map реализации

- Integration owner: публичные cmd/integration RED/GREEN, synthesis, docs,
  полный gate, последовательные Git/CI/deploy и live postflight.
- Native owner: только `internal/nativeadapter`, `internal/nativetranscript` и
  узко необходимый protocol DTO; owner model events после exact/FIFO user input,
  Codex и Claude exact-or-fallback.
- Card owner: только transport-neutral page/card projection packages после
  подтверждения фактического ingress seam; новый input всегда new carrier,
  latest/follow и сохранение старого carrier.
- Independent reviewers: read-only carrier race/restart и Claude transcript
  boundary. Критерий остановки - воспроизводимый публичный дефект, точный seam
  и существенные риски; live Telegram/provider writes запрещены.

Все исполнители используют неизменный договор выше. Один файл/пакет имеет одного
write-owner; integration owner проверяет изменения непосредственно в рабочей
папке и единолично выполняет release sequence.

## Реализация и evidence

- `nativeadapter` назначает commentary/tool/question/thinking и final последнему
  exact/FIFO-matched native user input; `sessionruntime` сохраняет durable
  message owner через steer, а controller использует его как history/output key.
- Prompt-карточка получает явный `OpenLatest`; slash-команды и обычное повторное
  открытие карточки не получают этот флаг и сохраняют текущий page plan.
- Все prepared send/edit сериализованы относительно durable send; перед прямым
  background edit под gate повторно проверяются carrier и revision. Prompt-status
  дополнительно ждёт commit carrier именно своего `status:<update>` и не трогает
  предыдущую карточку.
- Профильные тесты `nativeadapter`, `sessionruntime`, `telegramflow`,
  `telegrampromptcomposition` и joined navigation/final проходят. Полный
  `make check-full` 2026-09-11 GREEN, включая architecture, unit/integration,
  vet, packaging, race и executable-trio acceptance. Git/CI/deploy и live
  postflight ещё не выполнены.

## Следующая отдельная задача после A44 release

По указанию Артёма после перезапуска нужно найти точный опубликованный commit и
файл, из-за которых Git/CI сообщил о credential, проверить текущий tree и всю
достижимую историю. Обычное удаление из текущего tree разрешено как новая
разработка; переписывание опубликованной истории и force-push остаются отдельной
destructive последовательностью и требуют exact manifest перед выполнением.

## Отдельный повторяющийся дефект логов

Read-only обзор выявил 42 отдельных `session.provider_failure` одной операции
за 09:17-09:31 MSK 2026-09-11. Причина и влияние в A44 не установлены. Это
отдельный открытый дефект, который нельзя считать нормальным retry-фоном; после
выпуска A44 нужен самостоятельный RCA без смешивания scope.
